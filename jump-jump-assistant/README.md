# 微信"跳一跳"识别模块 — 最终交付

## 1. 任务定义
每帧识别两件事（这是玩法唯一需要的量）：
- **棋子底部中心**：棋子与所站方块接触的那一点 → 起跳点。
- **目标落点**：目标方块**顶面中心** → 落点。

跳距 = 棋子底部中心到落点的像素距离；按压时长 = 跳距 × 系数（真机标定一次）。
**目标方块永远在棋子上方（屏幕 y 更小）**——这是游戏规则，也是标注与推理的硬约束：
找不到上方方块就判为「无目标」，绝不退回选下方方块。

## 2. 方案
**YOLOv8n-pose 关键点检测**，单模型同时输出棋子与目标：2 类（`piece` / `target`）、
每类 1 个关键点（`kpt_shape=[1,3]`）。输入 640×640。
- 棋子标签用固定 60px 伪框（只有框中心有意义，框大小不代表棋子尺寸）。
- 目标标签为真实顶面框 + 顶面中心关键点。

顶面几何由**实测标定**：以棋子为锚（棋子底部中心站在所站方块顶面中心），
测得顶面框 高/宽 ≈ 0.507 ≈ 1/2，即标准 2:1 等轴投影，于是
顶面框 = `[顶点x − W/2, 顶点y, W, W/2]`、落点 = `(顶点x, 顶点y + W/4)`。
数据集内框宽中位 371px、高 186px。

## 3. 数据
- `screenshots/` 72 张真实截图（1080×2372），覆盖 3 套背景配色、多种方块皮肤。
- `annotations/` 71 份人工确认标注（唯一未标的是 `.trashed-*` 回收站文件，正确排除）。
- 切分：61 训练 / 10 验证。
- 预标注流水线 `auto_annotate2.py` 自动完成 64/72，其余 8 张由人工点击补齐。

预标注关键实现：
- 背景建模用**内侧边缘条带** `img[:,25:50]`、`img[:,w-50:w-25]` 估逐行梯度再纵向中值平滑，
  避免方块占据半行时把整行拉亮。
- 阴影按**乘法暗化**建模：`s=(p/bg).mean()`，`is_shadow = 0.6<s<1.02 & max|ratio−s|<0.07 & Δchroma<0.04`，
  再用边界 floodFill 补回被误判为阴影的方块内部孔洞。
- 顶面测量：水平 `MORPH_CLOSE(25,1)` 桥接同面断裂；顶点门限 `min_run=24` 跳过细尖突；
  行段容差 30px；粘连成一片时只看棋子所在行以上的部分再测。

## 4. 训练与最终指标

`python train.py` — YOLOv8n-pose，200 epoch，imgsz 640，batch 8，CPU。

验证集（10 张，PyTorch `best.pt`）：

| 指标 | Box | Pose |
| --- | --- | --- |
| mAP50 | **1.000** | **1.000** |
| mAP50-95 | 0.995 | 0.995 |
| Precision / Recall | 0.995 / 1.000 | 0.995 / 1.000 |

导出后的 NCNN 模型经官方路径复核（`yolo val`）：Box mAP50 0.995（mAP50-95 0.955）、
Pose mAP50 0.995（0.995），桌面 CPU 单帧 **37.5ms**。

**全量 72 帧对照人工标注**（`python eval_all.py`，跑的就是要交付的 NCNN 模型）：

| 目标 | 漏检 | 平均误差 | 中位 | 最大 | PCK@5px |
| --- | --- | --- | --- | --- | --- |
| 棋子 | 0 | **1.93px** | 1.78px | 4.13px | **100%** |
| 落点 | 0 | **8.67px** | 6.89px | 30.49px | 29.2% |

落点 8.67px 已远小于顶面短边（186px）的 1/4；PCK@5px 偏低是因为人工点击本身有 ±5px 量级
的抖动（阈值贴着标注噪声）。**「目标落在棋子下方」的违规帧 = 0**（修正标注前的模型是 7 帧、
平均误差 56.82px、最大 723.62px）。

### 4.1 用模拟器真实帧微调（`jump_pose_ft2`）

用安卓端实测采集的 254 帧真实游戏帧（1080×1920）回采训练：标签取**被落地结果验证过的**
模型预测（126 次成功落地即 126 次验证），再用与模型无关的 CV 等轴顶面测量交叉核对并剔除 15 帧。
与 71 张人工精标混合，从 `jump_pose-3` 续训 20 epoch（lr 0.001）。

| 指标 | 基线 `jump_pose-3` | 微调 `jump_pose_ft2` |
| --- | --- | --- |
| 人工精标 棋子 平均/PCK@5px | **1.93px / 100%** | 2.15px / 100% |
| 人工精标 落点 平均/PCK@5px/@10px | **8.67px** / 29.2% / 62.5% | 9.56px / **36.1% / 63.9%** |
| 违规帧 | 0 | 0 |
| 安卓端实战成功率 | 126/127（99.2%） | **160/161（99.4%）** |

`ft2` 额外学到模拟器域的方块皮肤（魔方、蜂巢、圆柱、细柱、WEDESIGN 盒）与 1080×1920 分辨率，
棋子类置信度更稳（留出集最小 0.87 vs 0.76）；但它**牺牲了未见皮肤上的泛化**：
在一帧训练集里没有的"白色环形方块"上目标类只给 0.34（低于阈值 0.35 漏检），基线在同帧给 0.76。

因此部署建议：**双模型取高置信的集成**（留出集上目标置信均值 0.924、最小 0.73，严格优于任一单模型，
代价是 2× 推理 ~75ms/帧）；单模型部署则用基线 `jump_pose-3`（127 跳实测 0 漏检）。

### 4.2 跨皮肤泛化（`jump_pose_hsv`）

把游戏皮肤换成"银色棋子 + 黄绿背景"后，目标类正常（0.87–0.95），但**棋子类整体塌陷**：
59 帧里 50 帧完全检不出，同一帧的棋子类分数从 0.9 掉到 0.004。关键点头其实仍然准确
（目视误差 5–7px）——塌的是**分类头**，它过度依赖"棋子是深紫色"这条颜色线索。

修复办法是**强颜色增广微调**（`hsv_h=0.5`、`hsv_s=0.7`、`hsv_v=0.5`，30 epoch），
用饱和度/亮度缩放造出"银灰棋子"，逼模型改用形状识别，**不需要采集新皮肤标签**：

| 指标 | 基线 | 颜色增广 |
| --- | --- | --- |
| 新皮肤 棋子检不出 | 50/59 | **5/59**（阈值 0.20 时 2/59） |
| 旧皮肤 棋子置信 均值/最小 | 0.915 / 0.509 | **0.932 / 0.901** |
| 人工精标 棋子 / 落点 PCK@5 | 100% / 29.2% | 95.8% / **38.9%** |
| 新皮肤实测连跳 | 10 跳即失败 | **38 跳 37 中** |

完整数据见 [`TEST_REPORT.md`](TEST_REPORT.md) §7。

## 5. 安卓端
- **推荐配置：双模型集成**——`runs/jump_pose_hsv/weights/best_ncnn_model/`（主，跨皮肤）+
  `runs/jump_pose-3/weights/best_ncnn_model/`（辅，药瓶类目标更强），每个类别各取置信度更高者。
  初始皮肤实测 **120 跳 120 中（100%）**，换皮肤后 60 跳 60 中。
  单模型则用 `jump_pose_hsv`。另外还有 `runs/jump_pose_ft2`（模拟器域微调版）可作参考。
  Windows 上无法导出 TFLite/LiteRT，故走 NCNN。
- 阈值按类别分开：**棋子 0.15 / 目标 0.35**（棋子类在换皮肤后分数会明显偏低）。
- 接口规格（**已实测**，非推测）：
  - 输入 `in0` = `1x3x640x640` float32，RGB、/255、**CHW 连续内存**；
  - letterbox = 等比缩放 + **居中**填 114（居中这点用同一张图与官方推理逐像素核对过，
    居中得 `(770.5,1086.0)`、官方得 `(770.6,1086.0)`；左上贴边会偏 16px 以上）；
  - 输出 `out0` = `(9,8400)` = `[0..3]`框 `xywh`(640空间) + `[4..5]`类别分 + `[6..8]`关键点 `x,y,conf`；
  - 回映：`orig = (coord640 − pad) / scale`。
- 代码与集成说明见 `android/README.md`：`JumpDetector.kt`（推理）、`JumpAssistService.kt`
  （无障碍 `dispatchGesture` 起跳）、`CaptureService.kt` + `MainActivity.kt`（截屏与悬浮窗）、
  `jni/jump_jni.cpp`（JNI 桥）、`CMakeLists.txt`、清单与无障碍配置片段。
- 按压时长 `press_ms = 跳距 × k`，`k` 必须在目标机型上标定（README 给了 3 组数据线性拟合的步骤）。

## 6. 脚本清单
```
label.py           人工标注工具(左键=落点, Enter=确认, 可断点续标)
auto_annotate2.py  预标注流水线(背景建模/阴影剔除/等轴顶面测量)
train.py           构建数据集 + 训练 + 导出 NCNN
eval.py            验证集关键点像素误差(PCK)
eval_all.py        全量评估: 对照人工标注 + 违规帧统计
detect.py          桌面参考实现, 与安卓端逐行对应(NCNN 推理 + 叠加可视化)
cmp_label.py       人工标注 vs 模型预测对比图
sheet_pred.py      预测叠加图分批对照表
make_sheets.py     人工标注分批对照表
sheet_labels.py    任意标注目录的分批对照表(支持真实帧伪标签)
probe_ncnn.py      NCNN 输入布局/letterbox 约定探针
probe_cand.py      原始候选探针: 打印各 anchor 的类别分与关键点(判定"漏检"是分数低还是没学到)
emu.py             安卓端单次闭环: 截屏→识别→按压→验证落点
emu_auto.py        自动连跳到失败, 记录 CSV(跳距/按压/置信度/是否落地)
emu_err.py         从落地帧反推落点偏差(用于校准系数)
build_emu_labels.py 真实游戏帧 → 伪标签(规则过滤 + CV 交叉核对)
finetune.py        混合微调(人工精标 + 真实帧伪标签) + 导出 NCNN
finetune_hsv.py    强颜色增广微调(跨皮肤泛化, 不需新皮肤标签)
collect_skin.py    换肤后采集器(检不到就自动点"再玩一局"重开)
eval_skin.py       跨皮肤评估(人工精标 / 旧皮肤 / 新皮肤三组)
eval_ensemble.py   集成评估(两个模型每类取高置信)
```

## 8. 这个目录在仓库里的位置

本项目是 [little-toys](../) 下的一个子目录，安卓工程在 [`android/`](android/)：

```bash
cd android && ./gradlew assembleDebug
# 产物 build/outputs/apk/debug/jump-assist-{arm64-v8a,x86_64}-debug.apk
```

安卓端的接口参数、悬浮窗用法、包体积账、构建坑（含 AGP 不接受 JDK 25、`ndk.abiFilters` 与
`splits.abi` 冲突）都写在 [`android/README.md`](android/README.md)。

**仓库里没有的东西**（体积大且可复现，已 gitignore）：`screenshots/`（72 张真实截图）、
`annotations/`（人工标注）、`dataset*/`、`emulator*/`（采集帧）、`runs/*`（训练产物）、
`models/`。要复现：先准备截图，跑 `auto_annotate2.py` 预标注 + `label.py` 人工补齐，
再 `train.py` 训练、`finetune_hsv.py` 颜色增广微调、导出 ONNX 放进 `android/src/main/assets/`。
`runs/jump_pose_hsv/weights/best.pt` 与 `runs/jump_pose-3/weights/best.pt` 是最终用的两个模型，
脚本里按这两个路径引用，已随仓库提供。

桌面端玩法闭环（需要连着安卓设备/模拟器）：

```bash
python play.py runs/jump_pose_hsv/weights/best.pt 5 1.35 3000   # k=1.35, 目标 3000 分
python app_monitor.py emulator/app.csv 300                      # 外部采样分数, 算命中中心率
```

按压系数换设备要重标：`k` 偏大会跳过、偏小会掉下去，用 `abtest.py` 做同局 A/B。

`detect.py` / `calib.py` 里仍保留着 NCNN 参考实现与路径，但**最终交付走的是 ONNX Runtime**
（见 `android/README.md`），NCNN 那条路是早期探索，读数只作对照。
