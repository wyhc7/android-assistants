# 安卓端实测报告 — 微信"跳一跳"识别模块

测试环境：MuMu 模拟器（1080×1920，density 480），微信小程序"跳一跳"。
按压通过 `adb shell input swipe x y x y <ms>` 注入——与 App 内
`AccessibilityService.dispatchGesture` 是同一动作（定点按压指定时长），
因此本报告验证的就是 App 的完整闭环：**截屏 → NCNN 识别 → 按压 → 落地**。

## 1. 稳定性实测（基线模型 `runs/jump_pose-3`）

连续自动跳，直到游戏失败：

| 项目 | 结果 |
| --- | --- |
| 连跳 | **126 连跳成功，第 127 跳失败**（游戏结束，本局 782 分） |
| 跳距范围 | 187–715px（均值 428px） |
| 棋子置信度 | 0.89–0.94 |
| 目标置信度 | 0.83–0.96 |

失败帧复核：目标是一根**细柱**（顶面框 110–127px 宽，容差仅 ±55–63px，约为普通方块的 1/4），
识别完全正确（`piece` 0.94 / `target` 0.91，落点正落在柱顶面中心）。
**失败原因是落点控制精度，不是识别**——这条结论决定了后续优化方向。

## 2. 用真实游戏帧回采训练数据

采集 254 帧真实游戏帧（127 起跳前 + 127 落地后），按以下规则生成伪标签：

- 标签值取模型预测，且该预测**被落地结果验证过**（126 次成功落地即 126 次标签验证），
  不是普通自训练；
- 硬规则：目标必须在棋子上方（`dy > 0`，实测最小 95px、中位 229px）；
- 目标顶面用**与模型无关的 CV 等轴测量**交叉核对，偏差 > 55px 的帧剔除；
- 模型置信度 < 0.55 的帧剔除。

最终采用 **239 帧**（剔除 15 帧）。与 71 张人工精标混合后微调：
从 `jump_pose-3` 续训，20 epoch，lr 0.001，batch 16，imgsz 640。

### 第一版微调的负结果（值得记录的坑）

第一版微调后，模型在**它自己的训练域**上都退化了：模拟器帧目标置信均值从 0.926 掉到
0.861、最小值 0.73 → 0.40，实战第 49 跳直接**漏检目标**（基线在同一帧 conf 0.84）。

根因是标签构建脚本的坐标格式 bug：`detect.py` 输出的 `box` 是 `[x1,y1,x2,y2]`，
而兜底分支把 `box[2]`（x2 坐标）当成了宽度，导致约 1/5 的帧目标框被放大 ~3 倍，
污染了 box 回归与类别置信度。修复为「关键点居中 + 精确 2:1 构框」后重建标签，
漏检帧恢复为可检出（conf 0.81）。

## 3. 修复后模型 `ft2` 的评估

| 指标 | 基线 `jump_pose-3` | 微调 `jump_pose_ft2` |
| --- | --- | --- |
| 人工精标 棋子 平均/中位/最大 | **1.93 / 1.78 / 4.13px** | 2.15 / 2.04 / 4.81px |
| 人工精标 棋子 PCK@5px | 100% | 100% |
| 人工精标 落点 平均/中位 | **8.67 / 6.89px** | 9.56 / 7.10px |
| 人工精标 落点 PCK@5px / @10px | 29.2% / 62.5% | **36.1% / 63.9%** |
| 「目标在棋子下方」违规帧 | 0 | 0 |
| 模拟器 48 帧 棋子置信均值 | 0.917 | **0.921** |
| 模拟器 48 帧 目标置信均值/最小 | **0.926 / 0.73** | 0.888 / 0.64 |
| 实战成功率 | 126/127（99.2%） | **160/161（99.4%）** |

两者在实战成功率上统计等价。`ft2` 多学了模拟器域的皮肤（魔方、蜂巢、圆柱、细柱、WEDESIGN 盒等）
与 1080×1920 分辨率，棋子类置信度更稳（最小 0.87 vs 0.76），人工精标上落点 PCK@5px 更高。

## 3.1 模型选择：干净留出集 + 集成

第 4 轮采集的 106 帧**全部晚于训练数据采集**，因此是干净的留出集：

| 目标类置信度 | 基线 | ft2 | 双模型取高（集成） |
| --- | --- | --- | --- |
| 均值 | 0.921 | 0.874 | **0.924** |
| 最小 | 0.53 | 0.68 | **0.73** |
| 棋子类 均值 / 最小 | 0.918 / 0.76 | 0.921 / 0.87 | **0.926 / 0.87** |

关键发现：微调**牺牲了未见皮肤上的泛化**。`ft2` 在一帧"白色环形方块"（该皮肤不在训练帧中）
上目标类只给 0.3405，低于部署阈值 0.35 而漏检；基线在同一帧给 0.7559，两个模型的定位几乎相同
（关键点 (501,939) vs (498,943)）。原因为微调把权重拉向已见皮肤，这是伪标签域适应的固有代价。

**集成（两个模型都跑，按置信度取高）在留出集的每一项上都严格占优**，并把最难帧从 0.34 救回 0.76。
代价是 2 倍推理（桌面 37.5ms → ~75ms/帧，仍远快于玩法所需的 ~500ms 决策窗口）。
安卓端 `JumpDetector` 支持双模型即可，模型资源 2×12MB。

NCNN 导出保真度：与 PyTorch 权重逐帧对比 24 组关键点，**平均偏差 0.63px**（23/24 在 0.7px 内，
一个 12.8px 的离群来自候选框选择差异，非系统性偏差）。

| 2 | ft2-v1（标签有 bug） | 49 | 48 | 起跳前目标漏检（标签 bug 所致，模型已废弃） |

| 4 | ft2 | 31 | 30 | 落地失败：最长跳 733.5px + 目标顶面 110px 宽 |

第 3–6 轮是同一次重开后的**单局连续游戏**：合计 **298 跳、1197 分**，期间未中途重启。

**两个最终模型的合计**：457 跳，落地失败 4 次（0.9%，全部是窄目标/距离极值下的控制误差），
识别漏检 1 次（0.2%，未见皮肤）。识别不是瓶颈。

## 4.1 稳定态的坑

重启/落地后游戏有入场与镜头动画，此时棋子位置不可信：在第 3 轮里，重启后 3 秒就起跳，
棋子被检到 y=1820（正常约 1000–1200），起跳直接失败。`emu_auto.py` 因此加了稳定态门
（连续两帧关键点差 ≤8px 才起跳）；**App 内也应做同样的判定**。

## 5. 控制系数

`press_ms = 跳距 × k`，实测 **k = 1.38 ms/px** 在 1080×1920 模拟器上可用
（跳距 167–750px 区间内成功率 99.4%）。残差来自落点控制精度：窄目标容差小，
系数误差随距离线性放大，因此后续若要继续提升，应优先精修 `k`（或用落地误差做闭环自适应），
而不是继续加训练数据。

## 7. 换皮肤实测与颜色不变性修复

换皮肤后（棋子从深紫变成**银色**、背景变黄绿）复测：

| 类别 | 旧皮肤 | 新皮肤 |
| --- | --- | --- |
| 目标类置信度 | 0.87–0.96 | **0.87–0.95（正常）** |
| 棋子类置信度 | 0.9 | **0.004–0.5（塌陷）** |
| 59 帧中棋子完全检不出 | 0 | **50 帧（85%）** |

关键点定位其实没坏：模型给出的棋子关键点目视误差只有 5–7px，塌掉的**只是分类头**——它过度依赖
"棋子是深紫色"这条颜色线索。试过三条绕路都不可靠：带掩码模板匹配（峰值落到方块上，0.63–0.72）、
只匹配球头（圆形对尺度不敏感，y 偏 22–63px）、直接取棋子类最高分候选的关键点（部分帧偏 57px）。

**修复：强颜色增广微调**（`hsv_h=0.5`、`hsv_s=0.7`、`hsv_v=0.5`，30 epoch，从基线续训），
**不采集任何新皮肤标签**——用饱和度/亮度缩放造出"银灰棋子"，逼模型改用形状识别。

| 指标 | 基线 | 颜色增广 |
| --- | --- | --- |
| 新皮肤 棋子检不出 | 50/59 | **5/59**（阈值放宽到 0.20 后 **2/59**） |
| 旧皮肤 棋子置信 均值/最小 | 0.915 / 0.509 | **0.932 / 0.901** |
| 人工精标 棋子 平均/PCK@5 | 1.93px / 100% | 1.97px / 95.8% |
| 人工精标 落点 平均/PCK@5 | 8.67px / 29.2% | **8.54px / 38.9%** |
| 新皮肤实测连跳 | 10 跳即失败 | **38 跳 37 中（97.4%）**，棋子置信 0.45–0.88 |

棋子类阈值单独放宽到 **0.20**（目标类仍 0.35）：新皮肤检出率 93%→97%，而在旧皮肤 80 帧上
**零变化**（无一帧因放宽而改变棋子位置，无误报风险）。

残余边界：银棋子站在**白色**方块上时对比度最低，分数约 0.35——正是 0.20 阈值覆盖的场景。

### 7.1 数据完整性教训

后续运行会覆盖 `emulator/a*_pre.png` 等同名帧，使 `annotations_emu/` 的标签与图片错配
（本次发现时 239 条全部错配）。已按时间戳把新皮肤帧分离到 `emulator_skin/`，并用当前图片
重建 218 条伪标签。**教训：采集帧必须按运行批次分目录命名，不能复用文件名。**

## 9. 初始皮肤复测与二次训练实验

换回初始皮肤后复测：34 跳全中（棋子置信 0.91–0.95），在第 35 跳前停下——因为出现了一个
**药瓶类目标**（右侧 WZC 瓶）。这一帧暴露了两个模型强弱互补：

| 帧 | 基线 | 颜色增广 |
| --- | --- | --- |
| 药瓶目标帧 `fail_pre_035` | 目标 **0.89** | 目标 0.30（漏检） |
| 银色棋子帧 `fail_post_010` | 棋子 0.05（漏检） | 棋子 **可检出** |

因此**集成（每类取置信度更高者）**是正确配置。用它跑初始皮肤：

| 配置 | 结果 |
| --- | --- |
| 颜色增广版单跑 | 34 跳 34 中，停在药瓶帧 |
| **集成（颜色增广 + 基线）** | **120 跳 120 中（100%）**，棋子置信 0.90–0.95、目标 0.78–0.96，棋子 <0.5 的帧 0 个 |
| 集成在换皮肤后 | 60 跳 60 中（100%） |

集成在人工精标 72 帧上：棋子 1.78px（PCK@5 97.2%）、落点 9.36px、违规 0。

### 9.1 二次训练的两个负结果（重要）

用本轮采集的初始皮肤帧（65 条伪标签，含药瓶帧）继续训练了两次，**都失败**：

| 实验 | 起点 | 颜色增广强度 | 药瓶帧 | 新皮肤 59 帧棋子检不出 |
| --- | --- | --- | --- | --- |
| v2 | 颜色增广版 | 温和 0.3/0.6/0.45 | — | **59/59（全废）** |
| v3 | 颜色增广版 | 强 0.5/0.7/0.5 | **0.87 ✓ 修好** | **59/59（全废）** |

即**只要把同皮肤（初始皮肤）数据并进续训，之前学到的颜色不变性就会被抹掉**（灾难性遗忘），
而初始皮肤本来就已经被充分覆盖（0.91–0.95），这些数据只贡献了负作用。v3 唯一的价值是证明了
药瓶帧可以被修正，代价是颜色鲁棒性全丢。

**结论：不把同皮肤数据继续喂给模型，改用集成**——两个模型互补，且都不需要牺牲原有能力。
只有将来要支持新皮肤时，才值得采集该皮肤的标签并按 §7 的强颜色增广重训。

## 11. 按压系数标定与最终验证(初始皮肤, 目标 3000 分 / 命中率 90%)

### 11.1 标定方法: 用分数增量做 A/B, 不用图像量测

早期用图像量测落点偏差(泛洪分割顶面、模板匹配)都不稳定: 泛洪结果随种子点漂移(同一帧不同
种子相差 50px, 还会漏到背景变成整屏), 模板匹配在纯色顶面上相关度退化(匹配分 1.000 却落在
屏幕边缘)。而**分数增量本身是游戏给的真值**: +1 = 普通落地, +2,4,6... = 命中中心(连续命中递增,
上限 32)。于是改成: 同一局内随机交替两个候选系数, 按跳距分档配对比较命中率 —— 任何常数量
的图像/链路偏差都被抵消, 比较无偏。

### 11.2 标定结果(每次按压 = k x 跳距, adb input swipe)

| k | 命中率 | 样本 | 备注 |
|------|--------|------|------|
| 1.31 | 44% | 31 | 短跳过短 |
| 1.33 | 68% | 38 | 与 1.35 同局配对, 直接可比 |
| 1.34 | 88.6% | 439 | 三轮池化 |
| **1.35** | **90.4%** | **198** | **最终采用** |
| 1.38 | 68% | 38 | 长跳(550-950px)只有 20%, 明显过冲 |

两个曾被当成"改进方向"的做法都被实验证伪, 已回退:
- **加正截距**(k=1.34, A=+30ms): 命中率 45%, 远差于 A=0 的 90%。
- **改用 sendevent 直接写 /dev/input**(本想绕开 adb 时序抖动): 它比 input swipe 多一段固定的
  按下事件开销, 最佳也只有 79%(A=-80), 两侧都掉, 反而更差。

### 11.3 最终验证(同一局从 0 分打到 3001 分, 中途未重开)

- 分数: **3001**(达成 >=3000)
- 跳数 198 | 命中中心 179 | 普通落地 19 | **命中率 90.4%**

### 11.4 修掉一个集成合并的坑(重要)

集成原本按"每类取最高置信"合并, 实测会出事: 基线模型把**棋子下方的方块**也识别成目标,
分数 0.82, 比 hsv 模型给出的正确目标 0.65 还高 —— 合并后目标跑到棋子下方, 触发"目标必须在
棋子上方"的规则, 结果被判成"无目标", 白白漏跳(实测连续 6 跳误判)。正确做法是
**几何规则要在合并之前对每个模型分别生效**: 先定棋子, 再只在"棋子上方"的候选里取最高分。
Python(calib.merge_ensemble)与 Android(JumpDetector.merge)都已按此修正。

### 11.5 结算与停止行为

- 结算判定要求**连续两帧**同时满足"识别不到棋子/目标 + 找到水平居中的白色胶囊按钮",
  避免画面上的白色方块被误判成"再玩一局"。
- 默认**结算即停**(不再自动续局); 连续识别失败也会止损退出。
- 兜底: 最近 20 跳命中率过低(<=3)判定参数跑飞, 立即停止。

## 12. 安卓 App(最终交付形态)实测

推理后端从 NCNN 换成 **ONNX Runtime**(本机没有 NDK, JNI/CMake 要多装一套工具链; ORT 只要一个
Gradle 依赖), 模型用 ultralytics 直接导出, I/O 与桌面 NCNN 版逐项对齐(`images` 1x3x640x640
float32 RGB/255 CHW → `output0` (1,9,8400))。

### 12.1 App 自身路径的成绩(全程无人工干预)

| 项 | 结果 |
| --- | --- |
| 最高分 | **4040**(显式读屏确认; 采样序列里 9880/84496 等是结算画面 ROI 误读, 已排除) |
| 命中中心率 | **90.2%(120/133)** 与 **89.9%(240/267)** 两次独立统计 |
| 连续表现 | 单局 97 跳、1221 分仍在继续; 之后一路打到 4040 |
| 按压系数 | `k=1.35`, 与桌面端一致(说明 dispatchGesture 与 adb input swipe 的时长语义基本等价) |

### 12.2 App 侧新增/修正

- **集成合并的顺序错误**: 原来按「每类取最高置信」合并, 基线模型会把棋子下方的方块识别成
  目标(0.82 > 正确目标的 0.65), 合并后目标跑到下方, 触发「目标必须在棋子上方」的规则被判成
  「无目标」, 实测连续 6 跳漏跳。改为**先定棋子, 再只在棋子上方取最高分**。
- **判稳**: 每跳前连抓两帧, 四组关键点坐标位移都 ≤6px 才认, 避免落地动画中途按出下一跳。
- **悬浮窗改成紧凑条**: 一个「▶ 连跳 / ■ 停止」按钮 + 一行状态, 默认贴右上角(天空区域,
  不压棋盘), 可拖动, 除这一小块外点击全部穿透。
- **运行时标定**: `am start ... --ef k 1.42` 直接改按压系数, 不必重新打包。
- **结算即停** + 连续识别失败止损; 启动顺序修正(`setContentView` 必须在 `showFloatWindow` 前,
  否则状态文字被 Activity 自己的 TextView 覆盖)。
- **MediaProjection 必须选「共享整个屏幕」**: 选「共享一个应用」时系统只给单应用画面, 与整屏
  VirtualDisplay 的实现不兼容。

## 13. 真机上"目标检不出"的根因与修复(0.35 → 0.20 + 兜底)

用户真机跑了很久(分数 4866)后停在"等待识别"不动。拿那一帧直接跑两个模型:

| 类别 | 颜色增广版 | 基线 |
| --- | --- | --- |
| 棋子 | 0.937 | 0.922 |
| 目标(药瓶类) | **0.347** | **0.057** |

棋子没问题, 是**目标类置信被 0.35 阈值挡掉**: 集成取最高分 0.347 < 0.35 → 整帧判成"无目标"。
目标阈值 0.35 从一开始就贴着实际分布 —— 药瓶类目标连颜色增广版也只有约 0.30, 只在模拟器上
靠基线模型的 0.89 兜住; 真机渲染(1080×2372, 宽高比与模拟器不同)把基线打到 0.057, 兜底就没了。

**修复**: 目标类阈值 0.35 → 0.20, 并且正常阈值下整帧检不出目标时, 用 0.08 再解一次同一份输出
(不重跑模型, 开销可忽略)。

**依据**:

| 验证 | 结果 |
| --- | --- |
| 72 张人工精标, 阈值 0.35 扫到 0.05 | 漏检/违规/落点误差**七档完全一致**(0 漏检 0 违规) |
| 400 张真实对局帧, 0.35 vs 0.20 vs 0.10 的落点选择 | **完全一致**(0 新增可跳、0 改选别的、0 都检不出) |
| 用户真机截图(原始失败帧) | 0.35 → 无目标; **0.20 → 棋子(615,1256) 落点(493,1169), 距离 149px → 按压 202ms** |

结论: 真正在过滤的是几何规则(落点必须在棋子上方), 置信度阈值只是多余闸门; 降到 0.20 在全部
可用数据上零代价, 却能救回真机上整类目标偏低的情况。

桌面侧同步改了 `emu.py`(新增 `TARGET_CONF=0.20` / `RELAX_TARGET_CONF=0.08` 与 `det_lo`)、
`calib.detect`(两级阈值)、`play.py` / `abtest.py`(同步建兜底检测器)。
